# Migrations

The source of truth for the database schema. Everything here is applied by
`scripts/migrate.py`, which records a checksum per file in
`app.schema_migrations` and refuses to continue if an already-applied file has
changed underneath it.

## Why these files look machine-generated

The schema was adopted from a working database that predated version control:
40 tables, 145 indexes, 260 constraints, 73 triggers and 55 RLS policies, built
over a long period with no migration history. There was no SQL in the
repository to adopt instead.

`scripts/adopt_schema.py` therefore dumps that database and splits the dump into
files by dependency order, because a `CREATE TABLE` cannot be reordered around
its own foreign keys by hand without a great deal of care. The result is
`000` through `070`.

`080` and `090` are hand-written:

- `080` corrects the adopted schema against product rules the original
  implementation had wrong. `position_count` was bounded at 2 rather than 5, it
  had no default, and nothing anywhere created the organiser's membership —
  an organiser could create an Ajo and never appear in it.
  `080`'s position-count constraint is added `NOT VALID`, on purpose. The
  database the schema was adopted from holds one three-member Ajo whose
  append-only ledger cannot be removed, and `NOT VALID` is the only option that
  both keeps that row and enforces the rule on everything written afterwards.
  See the comment in `080_ajo_size_bounds/001_position_count_bounds.sql`.
- `090` is the reference data. A schema-only dump carries no rows, which left
  `contribution_frequencies` empty and therefore `ajos.frequency_id` — a NOT NULL
  foreign key — impossible to satisfy. Generated by
  `scripts/seed_reference_data.py`.

## The two vocabularies called `actor_type`

`100` fixes the one bug in the adopted schema that the API was the first caller to
reach. `app.actor_type` is a GUC whose values are `anon` and `member`, and the RLS
policies compare against `member`. `audit_logs.actor_type` is a column whose CHECK
constraint allows `user`, `system`, `service` and `webhook`. `app.audit_row()`
passed the first straight into the second, so every audited write made with an
identity violated the constraint. The migration suite never set the GUC, so it
had always passed on the `service` default; the API is the first caller that sets
it. The mapping lives in `audit_row()` rather than in the API because the GUC
value is what the policies require.

`101` and `102` are the same lesson in a different place. `app.claim_email_
verification_token` runs with no identity -- the account being verified has no
session -- so the self-only SELECT policy matched nothing and the function
returned "invalid token" for every token. It then needed a second policy because
`SELECT ... FOR UPDATE` applies UPDATE policies as well as SELECT ones, and the
existing UPDATE policy had only a `WITH CHECK`. Both policies are scoped to
`ajo_migrator`, the function's owner; no application role can read the table.

## Rules

- **Never edit an applied file.** Add a new one. The checksum check exists to
  turn a silent divergence between environments into a loud failure.
- **Each file is one transaction.** The runner passes `--single-transaction` to
  `psql`, so a file that fails partway leaves nothing behind. No file here
  contains `BEGIN`/`COMMIT`; a file that cannot run in a transaction has to say
  so with a `-- no-transaction` marker.
- **Adopting a database that already has the schema is a separate operation.**
  `python3 scripts/migrate.py --db <name> --baseline 080` builds everything
  before `080` into a scratch database, compares it to the target with
  `scripts/compare_schemas.py`, and records the rows only on an exact match.
  Those rows are marked `baselined = true` with `duration_ms = 0`: the migration
  was verified, not run, and the ledger should not pretend otherwise.
- **Test against a real database.** `python3 scripts/test_migrations.py` builds a
  scratch database from these files alone and asserts the invariants. A rule
  enforced only in the domain code is a rule that the first direct SQL write will
  break.
- **Reference data is source, not fixture.** It is version-controlled because a
  database that disagrees with the repository about what payment channels exist
  is a deployment that behaves differently in production.
